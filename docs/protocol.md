# AION 2 wire protocol — findings

Status: Phase 1b decoder implemented (`src-tauri/src/decode.rs`, `events.rs`, `opcodes.json`; `re decode`). Layouts below were found in the `login2` capture and confirmed by deliberate-action captures (`nightmare-1`, `charswap`, `pets-1`, `pets-2`, `duty-3`, gear changes) or by consistency across recordings (see "Decoder"). No account data appears in this file; ids shown are game constants, values are placeholders.

## How to capture

1. Elevated terminal.
2. Fully quit AION 2.
3. `re record captures/<name> --seconds 600`, then launch the game, log in, stand still ~30 s.
4. `re dump captures/<name>.pcap --summary` (totals, entropy, gaps); `re dump <pcap>` for chunks with absolute timestamps.

To tie a field to a game fact, perform one deliberate action while recording (enter a dungeon, kill one monster, swap character, equip an item) and note its time.

A capture started while the game is already connected has no SYN, but it is still decodable: the server direction is not encrypted and the 10-byte server ping (`0e 00 36` + u64, every ~50 ms) is a frame-boundary anchor. Scan for that pattern and keep the first offset from which the varint chain runs to the end of the stream (`sync()` in `tools/re/aion_re.py`; checked on a mid-stream 8-minute capture: 32,642 frames chained 100%, 123 LZ4 containers). Starting before the game is still best because it also yields the handshake.

## Transport

- One TCP connection per game client to the game server's TCP port 13328. The local port changes per login.
- Passive capture of that port is enough; the login/website traffic is HTTPS on 443 and is not needed.

## Handshake (first two frames)

- Client → server, frame 1: contains an ASN.1 DER RSA public key (`30 82 01 08 02 82 01 01 00 …`, 264-byte DER, 2048-bit modulus).
- Server → client, frame 1: a ~280-byte blob (almost certainly the RSA-encrypted session key material).
- After that, **client → server frames look random** (entropy ≈ 7.7 bits/byte, no structure) → encrypted with the negotiated key. We cannot read what the client sends; we do not need to.
- **Server → client frames are not encrypted** in this capture (entropy ≈ 5.7, readable structure, plaintext strings after decompression). All game state flows this way, so passive decoding of server → client is viable.

## Frame layout (both directions)

```
frame = varint(V) body
total length of frame = len(varint) + V - 4
varint = 7 bits per byte, little-endian, MSB set = continues
```

Parsing a whole stream with this rule lands exactly on every frame boundary to the last byte in both directions. Reference capture (10 min, one character): 24,569 server frames in 844,669 bytes with 413 containers, 8,997 client frames. One TCP segment may hold part of a frame or several frames; always reassemble first.

Tooling: `re dump` (Rust, reference reassembler) and `tools/re/aion_re.py` (`chain`, `hist`, `findstr`, `findint`) reproduce these checks; see `tools/re/README.md`.

## Body

- First two bytes are the opcode. Hex of the two bytes in wire order: `00 36`, `1d 37`, `00 8d`, `04 38`, … The **second** byte clusters (`36`/`37`/`38` cover most traffic), the first varies: consistent with a **u16 little-endian** where the second byte is the high byte. Not yet proven; this file lists opcodes as wire-order hex (`op 0b61` = bytes `0b 61`).
- `00 36` = server ping: body is 10 bytes, `00 36` + u64 LE server time in epoch milliseconds, ~every 50 ms. The client answers with a 10-byte frame (encrypted).
- `ff ff` = **compressed container**: `ff ff` + u32 LE uncompressed size + one LZ4 block (block format, no frame header). Decompressed with the declared size, all 64 containers in the capture succeeded.
- A decompressed container is a plain sequence of frames using the same framing as above (varint, total = len + V - 4). It chained exactly to the end of the buffer in all 64 containers. No nested `ff ff`.
- Strings: u8 length prefix + UTF-8 bytes (character name seen as `08 <8 bytes>`).
- Login burst: the first container after the handshake is ~4.3 KB decompressed and carries the character name.

### Order at world entry (found by Phase 2a)

Per connection the server sends `56 36` combat power, `0b 61` counter snapshot, `56 e2` boards, `a5 ff` kinah, `1d 56` item level, `56 36`, `56 36`, and **then** `33 36` identity: the identity trails the bundle it describes (the boards and kinah were placed in the bundle by `duty-2`, and the same order is in `charswap` and `duty-1`). Evidence: replaying `charswap` (two characters on one connection) gives that sequence twice, and the second bundle precedes the second character's identity. Later events follow the same shape (`56 36` ×2, `0c 61`, `33 36`). A consumer therefore holds `56 36` and the snapshot until the next identity and attributes them to it; binding on the identity and applying later events files the second character's bundle under the first.

### Radar: monsters in view and the player's position (found in Pets 1B)

Server → client, after LZ4 flattening. **Positions are f32 in hundredths of a map unit** (the wire's value `/ 100` is the unit of `public/gamedata.json` `pet_monsters.spawns`; in the recordings monsters lie 0.3 to 2.4 units from the curated spawn points and their template ids are the `pet_monsters` keys). Entities are varints (monsters are above 16383, the player's own id below it in every capture).

| Opcode | Meaning | Layout (after the 2-byte opcode) |
|---|---|---|
| `41 36` | Monster spawn | `[varint entity][3 bytes][u32 template][2 bytes][f32 x][f32 y][f32 z][4 bytes]`, **12 more bytes when the first of the 2 bytes has bit 3**, then `[3 bytes]`**`[varint hp][varint max hp]`** and two equal u32 (not read), then more (the HP layout fits all 950 spawns of 7 captures; see "Target HP and stagger" in "Combat"). A **summon** (an entity owned by a player) uses the same opcode with a name after the 3 bytes, and further on repeats its entity as `[varint entity][01 02][f32 x][f32 y][f32 z][07 02 06][u32 owner]`; see "Combat" |
| `1b 37`, `1c 37` | Move | `[varint entity][u8 flags]`, **one extra byte when `flags & 1`**, then `[f32 x][f32 y][f32 z]`, then more |
| `1a 37` | Move | `[varint entity][2 bytes][f32 x][f32 y][f32 z]` |
| `3c 37` | Move (also players and the own entity) | `[varint entity][u8 flags = 03, no extra byte][f32 x][f32 y][f32 z]`, then more |
| `42 36` | Despawn | `[varint entity]` then 2 bytes. Sent in bulk at a map change (31 despawns for 15 monsters in view) |
| `21 36` | Map load: **the map id** | `[u32 load counter (1, 2, 3, ... per connection)][u32 map id][u32 instance][u32 0][f32 x][f32 y][f32 z]`, 48 bytes. Sent at world entry (before the identity) and at every map change, sometimes again inside the same map |
| `23 36` | Zone load: the player's own position | `[6 bytes 0][f32 x][f32 y][f32 z][6 bytes]`, 26 bytes |
| `2a 38`, `2b 38` | Skill frames | `[varint entity]` … and **the last 12 bytes are `[f32 x][f32 y][f32 z]`**. The position is the first entity's **only when that entity is the player's own** (the first varint of the `33 36` identity). Led by a monster it is somebody else's position (one point shared by several monsters in `pets-2`), so it is not used |

The player's position is **not streamed**: movement is client → server, which is encrypted. The exact fixes on the wire are the zone load, own-entity skill frames and own-entity `3c 37` moves; any other position is an inference from what is in view and is not used.

**Evidence:** monster spawns carry a template id and a position near the curated spawn points in `login2`, `pets-1`, `pets-2`, `duty-1`, `duty-3`, `charswap`, `nightmare-1` and `login`. The own-entity rule for skill frames comes from `pets-2`: a first reading that took the skill-frame position for monsters too put several monsters on one point while their spawns and moves had each elsewhere.

**Map id (`21 36`):** the second `u32` is present in `login2`, `duty-1`, `duty-2`, `duty-3`, `charswap`, `nightmare-1`, `pets-1` and `login` (`pets-2` starts mid-stream and has no `21 36`). Ids seen: `1010` is **Verteron** (the monsters in view in it are pet monsters spawning in `verteron`), `101001`, `151006`, `200003` and `210002` have no pet monster in view and are not regions. The ids of Altgard and Chaotic Lower Reshanta are **not known**: no capture was taken in them (experiment: record while entering each of them, see `docs/status.md`).

**Not known / limits:** a dead monster stays until its `42 36`, which can be a few seconds after it dies; the meaning of the bytes skipped in each frame; the radar's region comes from the map id of `21 36` (see below), or from the monsters in view when that id is not listed in `public/gamedata.json`. A capture that starts mid-stream has no identity, so no own entity and no player fixes from skill frames.

### Combat: the meter (found in Combat meter 1)

Server → client, after LZ4 flattening. Entities are varints (the player's own id is the first varint of the `33 36` identity); `amount` is a varint.

| Opcode | Meaning | Layout (after the 2-byte opcode) |
|---|---|---|
| `04 38` | Direct hit | `[varint target][u8 flags][u8 extra][varint attacker][u32 skill][u8 serial][u8 2, or 3 on a critical hit]`, **`[u8][varint][u8]` only when `flags & 2`** (3 bytes unless the varint is 128 or more), then `[u32 effect][u32][2-byte tag][varint amount]`, then the multi-hit list when `flags & 0x20` (`[u8 n][n varints]`), 2 bytes, and **`[varint heal]` when `extra & 4`** (a drain: it heals the attacker). **Damage only when `flags & 4`**: without that bit the amount is almost always 1 or 2 (12 larger in 1,600+ such frames) and the frame is not counted. Target = attacker: a self heal (see "Healing") |
| `05 38` | Tick (damage or heal over time) | `[varint target][u8 fields][varint attacker][varint serial][u32 effect]`, then by the bits of `fields`: 0 `[varint]` (what is left of a heal over time), 1 `[varint amount]`, 2 `[varint][u32]` (not read), 3 `[u32 skill]` |
| `00 8d` | HP and other stats of an entity | `[varint entity][u8 mask]`, bit 0: `[u8 n][n x (u8 stat, u32)]` (stat 1 is MP; others not known), bit 1: `[u8 n][n x (u8 stat, u64)]`, **stat 0 the HP, 7 the max HP**. Nothing follows (8,684 frames in `duty-2`, `duty-3`, `login`, `nightmare-1`, all parse exactly). Monsters get it too, HP only (never the max), from their first hit in the capture on |
| `05 e0` | A boss's stagger gauge | `[varint entity][u8 03][u8 01][u32 max][u32 value][u8 02]` (16 bytes) while it fills, **`[varint entity][00][03][02]`** (8 bytes) when it breaks; read as `[u8 fields][u8 state]`, state 1 filling, 3 broken. 576 frames, all of one of these two shapes, in `duty-2`, `duty-3`, `login`, `nightmare-1`, each on a boss |
| `45 36` | Another player came into view | `[varint entity][5 bytes][u8 n][name, n bytes UTF-8][u32 class code]`, then over 1 KiB not read except the tail (1,121 to 1,750 bytes in all; the 5th byte was `07` in all 136 frames of `login`, `duty-2`, `duty-3`). The class code is the identity's (`33 36`). **Combat power in the tail:** after a fixed marker come `[u32 item level][u32 count, absent at low levels][u32 combat power]` and 5 bytes, or 6 in some frames; so the power is the u32 at `len - 9`, or `len - 10` with the extra byte, found by checking that the u32 before it is a count (< 64) or an item level (800 to 2000). **Confirmed on `cp-1` (a party in a dungeon):** 4 players' powers equal the party window's, and the item level beside it is in the 1,000 to 1,200 range like the local one; all 36 spawn frames of the capture parse. The older `spirit-1` build has another tail (no marker), so the rule is for the current build; the extra byte is not understood. **A one-byte field (`01`) can sit between the count and the power** (`[item level][count][u8 01][power]` and 5 bytes): the u32 at `len - 10` then reads as the power x 256 + 1 (about 40 million), so a value of 2^24 or more is rejected and the power is the u32 at `len - 9` after the u32 at `len - 14`. Seen in a 40-player raid on 2 players, whose powers then equal the ones another meter saved for the same fight; a power under 65,536 behind that byte would still be misread |
| `47 36` | That player left the view | `[varint entity][2 bytes]` (decoded as a despawn, like `42 36`, which players never get) |
| `41 36` (summon) | A player's summon came into view | the spawn ends in `[varint][01 02][f32 x][f32 y][f32 z][07 02 06][u32 owner]`; found by searching for that shape (the fields before it vary in length and are not decoded). The varint is the summon's own entity for a Ranger's, **the owner's for a Spiritmaster's spirits** (`292xxxx` templates: Fire Spirit `2920101`, Water Spirit `2920121`), so it is not compared |

`skill` is the game's skill id plus a variant, taken raw (the frontend folds variants with `id / 10000 * 10000`). A summon's hits carry the summon as attacker and the summon's own skill variant (e.g. `14170037`); the meter credits them to the **owner** under the owner's skill (`14170000`). Frames of either opcode whose **target is its own attacker** are self effects: never damage, but heals (see "Healing").

**What counts as damage dealt.**
- A `04 38` needs `flags & 4`. With every `04 38`/`05 38` counted, 15 of the local player's skills in `duty-2` had extra hits of amount 1 from frames with `flags` `00` (or `02`); with the bit required they disappear.
- A summon's hits count for its owner. In `duty-2` one skill (`14170000`) had no hit by the player at all: its hits are `04 38` frames whose attacker is a summon (8 of them in `duty-2`, each a `41 36` naming the player as owner, 4 in `duty-3`, 1 for another player in `login`).
- The wire-only remainder of the first reading was self-targeted (attacker = target: 22,131 under one skill id, and ticks then misread because the `05 38` serial was taken as fixed bytes); those are heals.
- **Other players:** another player's hits count only on targets the local player or their summon has hit; the meter knows every player in view (the player's own identity and each `45 36` until its `47 36`). Hits of theirs before the local player's first hit on that target are dropped. In `login` one player's three hits landed 0.7 to 0.9 s before the local player's first hit on that monster, while their hits on monsters the local player never touched, over 130,000 in all, would otherwise fill fights with strangers.
- **Hits on players:** none of the seven meter captures has a hit whose target and attacker are both players (or their summons): 0 of the 7,159 decoded hits. Every heal recorded is self-targeted, so a heal on an ally is not known; with the hit layout it would parse as a hit. A hit on a player is therefore never counted as damage dealt (only as that player's damage taken); PvP and ally heals need a recording.

**Fights.** Every counted hit by or on the local player starts or extends a fight, so fight boundaries do not affect the local player's totals; a fight closes 10 s (capture clock) after its last counted hit or on a new connection (`docs/decisions.md`). **A boss gets its own fight:** a boss is a foe with a stagger gauge (`05 e0`) or a curated template ID. The roster combines the 521 bosses in Aion2Data's [global-client boss list](https://aion2data.com/bosses) (79 field bosses plus 442 Hero/Legend monsters, client 2.0.6.0) and the 85 field-boss IDs from the [current client-derived list](https://raw.githubusercontent.com/SkeeveAN/Aion-DPS-Meter/main/Client/assets/aion2/bosses/field_bosses.json), deduplicated to 528 IDs. The Aion2Data roster intentionally follows its broader definition, which includes Hero/Legend monsters beyond dungeon and raid encounter bosses. The first hit on one ends a fight that only had other foes, and a boss at 0 HP closes its fight at the first event more than 1 s after that instant (its killing hit arrives in the same instant, sometimes after the `00 8d`, and hits in flight land up to 0.15 s later). Without this the 10 s gap merged two bosses pulled back to back (one 6:36 fight for what a reference meter shows as two). Heals and other players' hits and damage taken never start or extend a fight.

**Summons of the Spiritmaster.** The spirits (Fire, Water, Earth, Ancient) attack with their own entity and skills `161x0001`/`16250001` (the summon skill's variant), `16001101` (shown as "Spiritmaster Weapon Equip" by the reference meter) and `100011..100055` (each spirit's basic attack, one id per spirit and level). In a Spiritmaster's fight (a reference meter's log of a Ferocious Horn Den boss) every other player's total matched ours to the unit, and the Spiritmaster's was 1.68M short of 5.25M: skills `1610`, `1611`, `1613`, `1625`, `1600` and the `100xxx` basic attacks, 1.63M of it, were not counted because their attacker was never taken for a summon (see the `41 36` row). In a new-account capture (`spirit-1`, level 3) the six spirit spawns all match the owner shape, none of the other 156 spawns do, and the spirits' hits are credited to the owner. One boss fight there (Lake Guardian, `2701034`) came out equal to the reference meter's log: 3,179 damage in 34 hits and 13.7 s, each of the 8 skills with the same amount. The boss reached 0 HP at 13.55 s and two more hits (a spirit's and the player's) landed 0.10 and 0.15 s later, so a fight stays open 1 s after its boss's death.

**Players in view (`45 36`).** Found by searching a capture for other players' names as text: in `login` (the only capture with other players: 3 of them) each name occurs in UTF-8 at offset 10 of a `45 36` frame whose leading varint is that player's entity, right after a length byte (the local player's name is never in a `45 36`; it is in the identity, and inside `41 36` summon frames, which carry their owner's name). The `u32` after the name is the class code: 18 Assassin and 30 Cleric (the codes `public/gamedata.json` and the local identity already use) and 25 Sorcerer. Codes seen across the three captures come in pairs 5/6, 9/10, 13/14, 17/18, 21/22, 25/26, 29/30, 33/34 (eight classes). A class code is a **range of codes per class**, not a pair: Gladiator 2 and 5-8, Templar 3 and 9-12, Ranger 4 and 13-16, Assassin 17-20, Spiritmaster 21-24, Sorcerer 25-28, Cleric 29-32, Chanter 33-36 and Brawler 45-48 (the later codes of a class are probably its specialisations; not decoded). That is consistent with the classes seen: 14 Ranger, 18 Assassin, 25 Sorcerer and 30 Cleric in `login`, and 8 Gladiator, 23 Spiritmaster and 28 Sorcerer seen in play (no capture kept). Each of the 95 `45 36` frames of `login` (60 players) is followed by a `47 36` for the same entity before that entity spawns again or the capture ends; `duty-2` 14 players, `duty-3` 16. Other players' names are confirmed on `login` only; elsewhere only the local player is seen, through the identity.

**Critical hits.** Bit 0 of the byte after the serial (read before as the high byte of a `u16` serial) is set on a critical hit: that byte is `02` or `03` in every damage `04 38` of `duty-2`, `duty-3`, `login` and `nightmare-1` (other values, `00`/`01`/`06`, only in frames without `flags & 4`). Of every bit from the flags to the trailer, this is the one that separates hits into two groups (159 and 217 hits across the four captures, found by correlating single hits with changes in a per-skill crit count during reverse engineering). `flags`, the optional field (`flags & 2`), the `u32 effect`, the tag and the multi-hit list all occur both ways. **Ticks (`05 38`) never count as critical**: the crit rate is critical hits over **direct** hits, and ticks are in the hit count but in neither crit count. In `duty-3` the one skill with ticks (`14050000`) shows a crit count that goes down at some direct non-critical hits, which only a critical-over-direct rate explains, and no bit of a tick's six bytes between target and amount, its amount (equal amounts occur both ways), nor the crit bit of the attacker's previous hit followed the counts. Whether the game itself crits ticks is not known (tick amounts of one damage-over-time vary by a few percent with no jump).

**Hits.** The hit count of a skill is **every counted hit, direct hits (drains included) and ticks**; the crit rate divides by direct hits only. A skill with ticks only on the wire (`13730000` in `login`: 59 ticks, no direct hit) has no rate.

**Healing.** Heals count whoever and wherever, not only on engaged targets. Every heal in the recordings is a self heal, and the raw amount on the wire is `healing + overheal`:
- **Drains:** a `04 38` damage hit whose `extra` byte has bit 2 ends with `[varint heal]` after the multi-hit list and the 2 bytes; it heals the attacker (`14380007`: 50 frames in `duty-2`, 37 in `nightmare-1`; another player's drains in `login`).
- **Self effects:** a `04 38` with `flags & 4` whose target is its attacker heals it by its amount (`14710007`, `13710007`, `2010101`, `17800001` for another player, and a restore `1900911`).
- **Heals over time:** a `05 38` tick whose target is its attacker heals it by the bit-1 amount; the bit-0 varint before it counts down what is left (`2102 -> 1682 -> ... -> 2` in steps of 420), and a frame with bit 0 alone announces it. Ticks without bit 3 carry no skill (`effect / 100` is used).
- **Not HP:** the `u32 effect` (the skill without its variant times 100, plus the effect's number) is the only thing that tells a restore's parts apart. These are excluded from healing: `19009112`, the second part of `1900911` (its amount is the MP that `00 8d` reports right after; `duty-2`, `nightmare-1`), `190000151` and `190000161` (`1721`, `99999`; `login`, `duty-3`; the `190000131` part is counted), and the Sorcerer self effect `1576000711` (another player's 17 frames of 25 in `login`). The reason for the ones other than `1900911` is inferred from the recordings, not confirmed in the game. They are listed by id: a new restore needs its ids added.
- **Overheal** is not on the wire: it is the part of the raw heal the HP had no room for, `min(raw, max - hp)` done, with HP and max from `00 8d` (max at world entry, sometimes before the identity, and when it changes) and HP raised by each heal until the next `00 8d`. Only the **local player's** HP is followed: other players' heals are all counted as healing with overheal 0. With HP unknown the heal counts as full overheal (the first drain after a zone change; the `00 8d` that follows is the damage taken after it); with the max unknown (`login` starts mid-stream) every heal is done.

**Damage taken.** No new frame: it is the `04 38`/`05 38` damage whose target is the player, with two findings:
- **The field after the crit byte is `[u8][varint][u8]`**, not 3 fixed bytes. In 4 damage `04 38` frames of `duty-2`, all on the local player, its first byte has bit 5 (`0x20`) and the varint takes 2 bytes (values 198 to 243); read as 3 bytes, the amount comes out as `78` (`0x4e`, a byte of the tag), read one byte later it is 998, 2,232, 1,215 and 993. One frame of `duty-3` has bit 5 with a 1-byte varint 0. The other 3,120 of the 3,125 damage frames with `flags & 2` in `duty-2`, `duty-3`, `login`, `nightmare-1` have bit 5 clear and a varint 0 (the first byte varies: `00`, `04`, `08`, `0c`, `80`, ...; the last is `00` to `02`). What the varint is (a shield's part?) is not known; it is not added to the amount.
- **Who counts:** every hit on the **local player** counts, whoever the attacker (in `duty-2` 2 of its 18 hits come from attackers never spawned in view). A hit on **another player** counts when its **attacker is in view** (a `41 36` spawn, a player or a summon, not yet despawned), whether or not the local player engaged it; this differs from damage dealt. This is the rule that fit `login` best (the only capture with other players): three hits on one player from an attacker that despawned 0.35 s before its hit or never spawned are not counted, and no simpler rule tried (engaged attacker, attacker hit by that player, time since the local player's last hit) separated them.

The live meter counts the player's own damage taken in every fight, and another player's in the current fight once they are in it (it neither starts nor extends a fight, like heals).

**Target HP and stagger.** The live fight carries the target (`entity`, `hp`, `max_hp`, `stagger`):
- **HP** is the monster's `00 8d` stat 0 (`00 8d` never carries a monster's max).
- **Max HP** is in the `41 36` spawn (row above): `[varint hp][varint max hp]` after the position and 3 bytes, found by searching the two `duty-2` bosses' max HP (2,160,000 and 2,280,000) as varints in their spawns. On the 17 targets first seen at full HP (the 4 bosses of `duty-2`, `nightmare-1`, `login`, and 13 small monsters of `login`) the spawn's max equals the HP before the first hit the capture shows (the first `00 8d` HP plus the hits of that instant); on the 25 others (hit before the capture, by others) that HP is below it, never above. The HP was below the max in 68 of the 950 spawns (already hurt). The spawn max is **not verified** against an independent value. A named spawn (bit 0 of the third byte) puts a name before the template; its HP is not read.
- **Stagger** is `05 e0` (row above): `(value, max)` while it fills, `(0, 0)` with `broken` true after a state-3 frame. A `locked` state is never seen on the wire.
- **Which target the fight shows:** keep the target while it lives; when it dies (HP 0), or at the fight's first hit, take the living monster the players dealt the most damage to, the frames of one instant counted together (ties to the highest entity; the most damaged dead foe when none lives). That rule fitted 1,640 of 1,667 recorded fight samples at their instant (9 more within a short lag); in two `login` fights (18 samples) the recorded target stays on a less damaged monster, perhaps a client-side selection that is not decoded. The live meter uses it (`Fight::pick`, a `ponytail`).

The live meter's fight JSON has `target: {entity, template, hp, max_hp, stagger: {state, value, max}}` (`null` until a monster is hit), kept with the finished fight.

**Not known:** whether the game crits ticks; what `flags` other than bits 1, 2 and 5 (`0x20`, the multi-hit list) mean, and what the frames without bit 2 are (misses or evasions?); the optional multi-hit list after the amount (it is not counted as extra damage); what the skill variant encodes; the rest of the `41 36` layout of a named spawn; the 5 bytes before a `45 36` name, everything after its class code, and the two bytes of `47 36`; whether a player in view is in the local player's group; which resource an effect restores (only the ids above are known); a drain with `flags & 0x50` (more fields before its trailer, none seen); heals of one player on another (none in the captures); the HP and max carried by the identity (`33 36`) and by `45 36` (after the position, at an offset that moves when a flag byte has bit 3, probably like `41 36`); the 3 bytes before a spawn's HP and the rest of its flag bits; the two `login` fights where the target pick differs.

## Decoder

- Resync retains a candidate until four supported frames can finish (up to 16 MiB total; each frame is capped at 4 MiB). The synthetic regression feeds a 100 KiB frame and a following combat-power event in one push and across pushes beyond 64 KiB, with identical decoded events and frame counts.
- `src-tauri/src/decode.rs`: reassembled bytes → `Framer` (varint framing, resync on the server ping `0e 00 36` when a stream starts mid-frame or after an abandoned TCP gap) → `ff ff` LZ4 containers inflated by an in-tree block decoder → frame bodies. `Decoder` joins `tcp::Streams`, the framer and the parsers; only server → client is decoded.
- `src-tauri/src/events.rs` + `src-tauri/opcodes.json`: opcode table keyed by build (`default`; wire-order hex) and the typed events (`Identity`, `CombatPower`, `ItemLevel`, `Boards`, `BoardEntry`, `KinahToday`, `DutyMissions`, `PassUsed`, `Counters`, `Counter`, `Pets`, `PetSoulsDelta`, `PetLevel`, `PetSoulsTotal`; radar `Spawn`, `Summon`, `PlayerSpawn`, `Pos`, `Cast`, `Gone`, `Teleport`, `MapEnter`; combat `Hit`, `Heal`, `Hp`, `Stagger`). Raw ids and values only.
- `re decode <pcap>` prints one JSON object per event (contains character names: do not paste it).
- Frame/container cross-check against `tools/re/aion_re.py chain`: `login2` 24,569 frames / 413 containers (exact); `nightmare-1` (3 connections) 15,961 / 47 (exact sum); `pets-2` (mid-stream) 33,878 vs 33,879 frames (the frame before the first ping, kept by the Python tool because that capture began on a boundary), 271 containers (exact). No container failed to inflate.
- Gains (Supply Emergency daily/weekly, kinah today) are stored per character. The boards and the kinah snapshot precede the identity they belong to, so `replay` holds gain values from a counter snapshot until the next identity (counters are still attributed as before).

## Not yet known

Each item below is an experiment to run with a deliberate in-game action while `re record` is running (start it before the game when possible).

- **Deaths (not located).** No capture has a death, so there is nothing to search yet, and the meter leaves deaths out. Experiment: die once in a dungeon or field, one action, and look for a frame at that instant that names the player's entity.
- **Absorption and spiritstones (not located).** No capture has an absorb shield or a spiritstone in use, and the meter leaves both out. The varint with bit 5 in the `04 38` optional field (see "Damage taken": 4 hits on the local player in `duty-2`, 198 to 243) is not known to be an absorb. Experiments, one action each: **take damage while an absorb shield is active** (a shield skill or item on the player, then a hit from a monster) and compare the hit frame with the unshielded ones; **use a spiritstone**. What a spiritstone does in the game is a hypothesis from the name only (it may be the healing or shielding such an item gives); try a healing or shield consumable whose name says spiritstone and look for the frame before searching further.
- Opcode width/endianness (see Body) and the full table (opcodes are remapped per game build; we build ours from correlations with deliberate actions).
- cap/next-refill derivation for counters, the trailing sub-lists of `0b 61`/`24 e3`, the meaning of the `2a38` family (`45 36` is a player spawn, see "Combat") (many small frames; `2a38` varies like combat events).
- Whether anything needs the client direction (assumed no).
- Whether other servers/regions use the same port and framing.
- The second `u64` of a refilling time counter (3,600,000 ms was seen next to a 25,200,000 ms cap, probably the refill period, discarded) and what the record's `charged` varint means in the game. `0c 61` shares the `0b 61` record layout; the meaning of its leading `00` byte and of the trailer byte (`02`/`03`) is unknown. Experiment: spend one counter once per kind of ticket and compare `charged` before and after.
- `24 e3`: the meaning of `a`, `ms`, `x`, the three sub-lists and the tag byte (all skipped), and the 14-byte `23 e3` frame (`[op][u16 0][u32 10044][6 bytes]`) seen once in `login2`, not tied to a value change (a reward-claim reply?). Experiment: claim a Daeva Pass reward and look for `23 e3`.
- **Membership expiry.** The account's membership expiry is **not in the recorded server stream**: an exact scan of `login2` and `charswap` (with handshake) found no u32/u64 in seconds, ms, µs or FILETIME, in UTC offsets of ±14 h in 15-minute steps, no text date, and no "expiry minus N whole days" (N ≤ 400) start. Remaining-duration scans are pure noise at this tolerance and prove nothing. A premium-dependent cap (Shugo Festival keys 12/21, Odyle Energy 560/840) therefore cannot be switched from the wire yet, and the caps assume premium. Experiment: note the in-game days left, record from before login and scan for that instant in the encodings above.
- **Daily attendance (not located).** Two claims make up the count (the daily board and an event board, counted together; the daily is claimed first). In `attendance-1` they were claimed one after the other as deliberate actions, and each coincided with a packet carrying `1b 56` and `8a 56`. Both are generic item-gain frames, not attendance: `1b 56` appears in nearly every capture and `8a 56` also in `pets-1`/`pets-2` with another layout, with no attendance claim. Nothing at world entry carries the 0/1/2 state: a same-day, same-character diff of the entry frames of `attendance-1` (nothing claimed) and `attendance-2` (both claimed) shows only inventory (`11 56`, `5b 8d`, `7e 8d` gained item instances), equipment rolls (`8c e2`), entity ids and timestamps; `53 8d` (the `Attendance_Group_*`, `battlepass_*` names) is static and byte-identical in both. A byte-offset search for a 0/1/1/2 pattern across `attendance-1`, `duty-1`, `charswap` and `duty-2` found none, and `4b 56` (a list of u32 ids: 3, 2, then 0 on the older days) does not follow the value. Experiment: after the daily reset, record before the first login, claim only the daily, then relog on the same character; the two entries differ in the daily alone, and the claim gives a second `1b 56`/`8a 56` sample.
